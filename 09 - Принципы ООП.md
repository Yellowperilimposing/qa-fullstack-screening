## 9. Принципы ООП

> [!abstract] Коротко
> ООП — объектно-ориентированное программирование.


**ООП** — объектно-ориентированное программирование.
Главная идея ООП: программа строится из **объектов**, которые имеют **данные** и **поведение**.

Например, объект `User`:

* данные: `name`, `age`, `email`;
* поведение: `login()`, `logout()`, `changePassword()`.

В ООП есть 4 основных принципа:

1. инкапсуляция;
2. наследование;
3. полиморфизм;
4. абстракция.

---

### 9.1. Инкапсуляция

**Инкапсуляция** — это сокрытие внутренней реализации объекта и доступ к данным через методы.

Простыми словами: поля класса часто делают `private`, а доступ к ним дают через методы `get` и `set`.

```java
public class User {
    private String name;

    public String getName() {
        return name;
    }

    public void setName(String userName) {
        name = userName;
    }
}
```

Использование:

```java
User user = new User();

user.setName("Danil");

System.out.println(user.getName());
```

Зачем нужна инкапсуляция:

* защищает данные от неправильного изменения;
* скрывает внутреннюю реализацию;
* делает код безопаснее и понятнее;
* позволяет контролировать изменение полей.

Пример с проверкой:

```java
public class User {
    private int age;

    public void setAge(int userAge) {
        if (userAge >= 0) {
            age = userAge;
        }
    }

    public int getAge() {
        return age;
    }
}
```

Если бы поле `age` было публичным, туда можно было бы записать неправильное значение:

```java
user.age = -100; // плохо
```

---

### 9.2. Наследование

**Наследование** — это механизм, при котором один класс получает поля и методы другого класса.

Класс-родитель называется **superclass** или **parent class**.
Класс-потомок называется **subclass** или **child class**.

Пример:

```java
public class Animal {
    public void eat() {
        System.out.println("Животное ест");
    }
}
```

```java
public class Cat extends Animal {
    public void meow() {
        System.out.println("Кот мяукает");
    }
}
```

Использование:

```java
Cat cat = new Cat();

cat.eat();
cat.meow();
```

Результат:

```text
Животное ест
Кот мяукает
```

Зачем нужно наследование:

* чтобы не дублировать общий код;
* чтобы выделять общую логику в родительский класс;
* чтобы строить иерархию классов.

Пример из тестирования:

```java
public class BaseTest {
    public void openBrowser() {
        System.out.println("Открываем браузер");
    }
}
```

```java
public class LoginTest extends BaseTest {
    public void checkLogin() {
        openBrowser();
        System.out.println("Проверяем логин");
    }
}
```

### 9.3. Полиморфизм

**Полиморфизм** — это возможность использовать один интерфейс или родительский тип для разных реализаций.

Простыми словами: один и тот же метод может работать по-разному у разных объектов.

Пример:

```java
public class Animal {
    public void makeSound() {
        System.out.println("Животное издаёт звук");
    }
}
```

```java
public class Cat extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Мяу");
    }
}
```

```java
public class Dog extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Гав");
    }
}
```

Использование:

```java
Animal cat = new Cat();
Animal dog = new Dog();

cat.makeSound();
dog.makeSound();
```

Результат:

```text
Мяу
Гав
```

Зачем нужен полиморфизм:

* позволяет писать гибкий код;
* можно работать с разными объектами через общий тип;
* удобно расширять программу без переписывания старого кода.

---

### 9.4. Абстракция

**Абстракция** — это выделение главного и скрытие лишних деталей.

Простыми словами: мы описываем, **что объект должен делать**, но не всегда сразу описываем, **как именно он это делает**.

В Java абстракция реализуется через:

* `abstract class`;
* `interface`.

Пример через абстрактный класс:

```java
public abstract class Animal {
    public abstract void makeSound();

    public void eat() {
        System.out.println("Животное ест");
    }
}
```

```java
public class Cat extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Мяу");
    }
}
```

Пример через интерфейс:

```java
public interface PaymentService {
    void pay();
}
```

```java
public class CardPaymentService implements PaymentService {
    @Override
    public void pay() {
        System.out.println("Оплата картой");
    }
}
```

Зачем нужна абстракция:

* скрывает лишние детали;
* помогает проектировать архитектуру;
* позволяет работать не с конкретной реализацией, а с общим контрактом.

### 9.5. SOLID

**SOLID** — это пять принципов проектирования объектно-ориентированного кода.

Они помогают писать код, который проще:

* читать;
* тестировать;
* расширять;
* поддерживать;
* менять без поломки старой логики.

---

#### 9.5.1. S — Single Responsibility Principle

**Принцип единственной ответственности.**

У класса должна быть одна основная причина для изменения.

Простыми словами: один класс должен отвечать за одну задачу.

Плохо:

```java
public class UserService {
    public void createUser() {
        // создать пользователя
    }

    public void sendEmail() {
        // отправить email
    }

    public void saveReport() {
        // сохранить отчет
    }
}
```

Лучше разделить ответственность:

```java
public class UserService {
    public void createUser() {
        // создать пользователя
    }
}

public class EmailService {
    public void sendEmail() {
        // отправить email
    }
}
```

---

#### 9.5.2. O — Open/Closed Principle

**Принцип открытости/закрытости.**

Код должен быть открыт для расширения, но закрыт для изменения.

Простыми словами: новую логику лучше добавлять через новые классы или реализации, а не переписывать старый рабочий код.

Пример: если есть разные способы оплаты, лучше сделать общий интерфейс:

```java
public interface PaymentService {
    void pay();
}
```

И отдельные реализации:

```java
public class CardPaymentService implements PaymentService {
    public void pay() {
        System.out.println("Оплата картой");
    }
}

public class CashPaymentService implements PaymentService {
    public void pay() {
        System.out.println("Оплата наличными");
    }
}
```

---

#### 9.5.3. L — Liskov Substitution Principle

**Принцип подстановки Лисков.**

Объект дочернего класса должен нормально заменять объект родительского класса.

Простыми словами: если код работает с родительским типом, то любая дочерняя реализация не должна ломать ожидаемое поведение.

Пример:

```java
Animal animal = new Cat();
animal.makeSound();
```

Если `Cat` наследуется от `Animal`, она должна вести себя как корректное животное в рамках контракта `Animal`.

---

#### 9.5.4. I — Interface Segregation Principle

**Принцип разделения интерфейсов.**

Лучше несколько маленьких интерфейсов, чем один большой интерфейс на все случаи.

Плохо:

```java
public interface Worker {
    void code();
    void test();
    void deploy();
}
```

Если классу нужен только `test()`, он не должен зависеть от `code()` и `deploy()`.

Лучше:

```java
public interface Tester {
    void test();
}

public interface Developer {
    void code();
}
```

---

#### 9.5.5. D — Dependency Inversion Principle

**Принцип инверсии зависимостей.**

Классы должны зависеть от абстракций, а не от конкретных реализаций.

Простыми словами: лучше зависеть от интерфейса, а конкретную реализацию подставлять отдельно.

```java
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void payOrder() {
        paymentService.pay();
    }
}
```

Так `OrderService` не знает, какая именно оплата используется: картой, наличными или другим способом.

---

### 9.6. Коротко про SOLID для скрининга

SOLID — это набор из пяти принципов ООП-дизайна:

| Буква | Принцип | Коротко |
| --- | --- | --- |
| S | Single Responsibility | Один класс — одна ответственность |
| O | Open/Closed | Расширяем поведение без изменения старого кода |
| L | Liskov Substitution | Наследник должен заменять родителя без поломки логики |
| I | Interface Segregation | Лучше маленькие интерфейсы, чем один большой |
| D | Dependency Inversion | Зависим от абстракций, а не от конкретных классов |

Ответ на скрининге:

SOLID нужен, чтобы код был гибким, поддерживаемым и тестируемым. Эти принципы помогают разделять ответственность, избегать сильной связанности и проще расширять систему.
